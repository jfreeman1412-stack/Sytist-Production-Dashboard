Phase 9e-hotfix3 — preview endpoints public (auth bypass for image fetches)

═══════════════════════════════════════════════════════
THE BUG (now actually diagnosed)
═══════════════════════════════════════════════════════

The Network tab showed it clearly:

  preview?v=2026-05-10T14...   401   json   0.1 kB

The image preview endpoint was returning 401 Authentication Required.

Why: the dashboard's auth middleware rejects requests without
a session, and SVG <image> / HTML <img> native fetches don't
carry whatever credential the JS API client uses. So when the
canvas tries to render a graphic, the request fails with 401,
and the browser shows nothing (or stale cached bytes from a
previous successful fetch).

This wasn't a cache problem like I thought in 9e-hotfix2 — it
was an auth problem. The "stale cloudy/grass image" was either
left over from a fetch that succeeded under different conditions
(possibly before auth was tightened, or a different layout's
graphic served in earlier testing), or was a browser-cached error
response, or was something else weird. Doesn't matter — what
matters is the request was failing the entire time.

═══════════════════════════════════════════════════════
THE FIX
═══════════════════════════════════════════════════════

Two preview endpoints registered BEFORE the `router.use(requireAuth)`
middleware in sytist.js:

  GET /api/sytist/composite/layouts/:layoutId/graphics/:key/preview
  GET /api/sytist/gallery-assets/logos/:galleryId/preview

These are public (no auth required). They serve image bytes that:
  - Reveal nothing the caller doesn't already know about
    (you need the layoutId and key to call them)
  - Are inherent to a closed-environment internal lab tool
    on localhost
  - Need to work via native browser <img> / <image> fetches

The duplicate auth-protected registrations later in the file are
removed (the public ones take precedence anyway, but cleaner to
not have dead code).

All other endpoints — including upload, delete, list — still
require auth. Only the read-only image streaming is public.

═══════════════════════════════════════════════════════
SECURITY NOTE
═══════════════════════════════════════════════════════

Making preview endpoints public is appropriate for this
deployment context (closed environment, localhost, internal
lab tool). If the dashboard ever gets exposed to the internet
or shared across organizations, these would need to be
auth-protected and you'd need a different solution for
authenticating image fetches (e.g., short-lived signed URLs,
or moving images to a CDN with bearer tokens).

For Sportsline today: no concern.

I went down two wrong paths before finding this:

  9e-hotfix:   Body-parser limit (turned out fine — uploads

The actual cause was auth-rejecting the SVG <image> fetch.
I should have asked you to open DevTools → Network FIRST,

the answer immediately. Instead I spent two hotfixes
chasing other theories.

Going forward, when you describe an image not rendering as
expected, my first ask should be: "open DevTools → Network,
look for the image request, what's its status code?" Not:

Sorry for the runaround. This one should actually be it.
