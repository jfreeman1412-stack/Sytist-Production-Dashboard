═══════════════════════════════════════════════════════
WHAT THIS DOES
═══════════════════════════════════════════════════════

When an order has already been processed (Sytist status 40 =
Printing, or 39 = Shipped), the dashboard now treats a click of
the Process button as a REPRINT instead of a fresh print:

  - Output filenames get a _REPRINT[_N] suffix
       110685.txt                      ← original
       110685_REPRINT.txt              ← 1st reprint
       110685_REPRINT_2.txt            ← 2nd reprint
       110685_REPRINT_3.txt            ← 3rd reprint

  - Sytist status is NOT changed (stays at 39 or 40)

  - ShipStation is NOT touched (no auto-create, no update)

  - An audit row is written with source='reprint' so the history
    of every reprint event is preserved

The Process button itself adapts: when the order is in reprint
state, it changes color (orange) and label ("Reprint this
order"), and a confirm dialog appears before clicking (since
reprints are less-routine and the operator should explicitly
opt in each time).

═══════════════════════════════════════════════════════
PER-ITEM REPRINT
═══════════════════════════════════════════════════════

Each line item card gets a "Reprint this item" button (orange)
in the same row as "Render preview". The button is ONLY visible
when the order is in reprint state (status 39 or 40) — for
fresh orders it stays hidden so it doesn't tempt operators into
unnecessary fragmentation.

Clicking it:
  1. Asks for confirmation
  2. Calls POST /api/sytist/process/order/:orderId/reprint-item/:cartId
  3. Runs processOrder with reprint:true + lineItemFilter:[cartId]
  4. Produces ONLY:
       - One imposed sheet for this cartId
       - One .txt referencing only this line item
     No packing slip (you decided single-item reprints don't
     need one — the operator already knows what they're
     reprinting).
  5. Returns success with paths to the new files, displayed in
     a small orange banner under the line item card.

Filenames include both the reprint suffix AND the cartId so
multiple per-item reprints don't collide:
  110685_481629_REPRINT_JV_Baseball-0016.png
  110685_481629_REPRINT_2_JV_Baseball-0016.png

═══════════════════════════════════════════════════════
REPRINT STATE DETECTION
═══════════════════════════════════════════════════════

Detection is based on Sytist order_open_status:
  - 0 (Open/Queue)   → fresh: "Process this order" (blue button)
  - 40 (Printing)    → reprint: "Reprint this order" (orange)
  - 39 (Shipped)     → reprint: "Reprint this order" (orange)

The dashboard reads order.productionStatus.id from its canonical
order shape. No new fields, no new tables.

For multiple reprints, the server's _nextReprintNumber() helper
scans the output dir for existing _REPRINT files for that
orderNumber and picks the next available N. So you can reprint
the same order 5 times and end up with _REPRINT, _REPRINT_2,
_REPRINT_3, _REPRINT_4, _REPRINT_5 — each gets its own clean set
of files.

═══════════════════════════════════════════════════════
KNOWN LIMITATIONS / FUTURE WORK
═══════════════════════════════════════════════════════

  - The _nextReprintNumber() helper looks at the regular download
    dir only. If a previous reprint went to a different folder
    (different folder-sort config, different mode, etc.), it
    won't see those files and may pick a colliding number. In
    practice this is rare because the folder-sort + mode are
    typically stable for the same gallery.

  - For ship_to_managers / ship_to_league orders that get split
    into per-team sub-orders, each sub-order writes its own
    _REPRINT files. The numbering is per-team-folder, not global,
    so a multi-team reprint produces _REPRINT in each team's
    folder (which is what you want).

  - The per-item reprint button is only shown when status is 39
    or 40. If you ever want to print just one item out of a
    fresh order, you'd currently need to Process the whole order,
    then come back and use the per-item button. We can flip that
    decision in a future phase if it becomes annoying.

  - Audit rows for reprints use to_status=0 + from_status=null
    since reprints don't change the status. The 'notes' column
    is where the meaningful data lives ('REPRINT_N items=...
    reason="..."'). Filter for source='reprint' to find them.

  - No "reason" field is currently exposed in the UI. If you
    want to track WHY each reprint happened (damaged in shipping,
    wrong photo selected, etc.), let me know and I'll add a
    reason input to both reprint confirm dialogs. The server-side
    plumbing is already in place — just need to wire up the UI.
