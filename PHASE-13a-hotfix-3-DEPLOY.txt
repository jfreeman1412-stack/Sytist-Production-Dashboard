DESIGN NOTE: WHY ROUTE FILE OWNS THE AUTH
═══════════════════════════════════════════════════════

I had two patterns to choose from:

  (a) Apply requireAuth at the mount point in server/index.js
  (b) Apply requireAuth inside the route file with router.use()

I went with (b) because:

  - It matches how routes/sytist.js does it (consistency)
  - It eliminates a class of mistake: forgetting to add the
    auth middleware at mount time, leaving endpoints public
  - The Phase 13a deploy notes asked you to add requireAuth
    at the mount, which means it WAS the operator's job to
    get this right — moving it inside the route file makes
    that job impossible to forget

Trade-off: if someone in the future wants ONE route in this
file to be public (e.g. an unauthenticated webhook from
ShipStation), they'd need to put it ABOVE the router.use()
line. That's the same constraint sytist.js handles for its
public preview endpoint, and it's well-precedented.
