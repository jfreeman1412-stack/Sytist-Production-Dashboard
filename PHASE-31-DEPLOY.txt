Phase 31 — Push packaging info to ShipStation when adopting an
          existing SS order

═══════════════════════════════════════════════════════
WHAT THIS DOES
═══════════════════════════════════════════════════════

When you Process an order that ALREADY exists on the ShipStation
side (created manually by an operator, or by an earlier version
of the dashboard that didn't compute packaging), the dashboard
used to:

  1. Compute fresh packaging (weight, dimensions, carrier, service)
  2. See that an SS order exists with the same orderNumber
  3. Link the local row to it
  4. Return "adopted_existing" — WITHOUT pushing the new
     packaging to SS

The result: ShipStation kept whatever blank/default values it had
from the original create. The operator saw no weight, no carrier,
no package on the SS side.

After Phase 31, the adopt-existing path ALSO sends the new
packaging payload to ShipStation as an upsert (using their
/orders/createorder endpoint with the existing orderId, which
ShipStation treats as an update). Now the freshly-computed weight,
dimensions, carrier, service, package code all land on the SS
side every time you process.

This is the same behavior you'd get on a fresh create, just
applied to existing SS orders too.

═══════════════════════════════════════════════════════
BEHAVIOR
═══════════════════════════════════════════════════════

ADOPT + UPDATE FLOW:
  1. Compute packaging payload (existing logic)
  2. List SS orders by orderNumber
  3. Found one? Call createOrder with payload + orderId of the
     existing SS order. SS treats this as an update.
  4. Insert / update the local link row with carrier/service/
     package codes from the payload (these used to be NULL on
     adopted links — Phase 31 fixes that too).
  5. Return success — message indicates whether the packaging
     update succeeded or failed.

FAILURE HANDLING:
  - If the update API call fails (network, auth, SS rejection),
    the adoption itself still succeeds. The link row gets
    created so future operations know the SS order exists.
  - A warning logs the failure: "[Processing] Order N adopted
    SS#X but packaging update failed: <reason>"
  - The result object includes `packagingUpdated: false` and
    `packagingUpdateError: "<reason>"` so callers can react.

OVERWRITE BEHAVIOR:
  - Per the operator's preference (asked during spec), this
    ALWAYS overwrites whatever's on the SS side, even if the
    operator manually edited fields in ShipStation. Trade-off:
    consistent dashboard-driven packaging vs respecting manual
    edits. We chose consistency.
  - If you want to preserve manual edits in the future, we can
    add a "preserveManualEdits" setting that diffs against the
    existing SS order before pushing.

    - The adopt-existing branch (around line 415) now:
      1. Builds an upsert payload: { ...payload, orderId: found.orderId }
      2. Calls shipstationService.createOrder(updatePayload)
      3. Logs success or failure with packageCode/weight/carrier

         path)
      4. Passes carrierCode/serviceCode/packageCode to the link
         row insert (previously left NULL)
      5. Returns enriched result: packagingUpdated bool,
         packagingUpdateError string when applicable
