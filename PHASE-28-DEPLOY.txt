Phase 28 — Order status transitions (Mark Shipped / Mark Back to Printing)

═══════════════════════════════════════════════════════
WHAT THIS DOES
═══════════════════════════════════════════════════════

Adds the ability to flip an order's production status to "Shipped"
(status_id 39) and reverse it back to "Printing" (status_id 40) if
needed. Two trigger surfaces:

  1. PER-ORDER on the order detail page — a new "Production Status"
     card with a "Mark Shipped" button when the order is in
     Printing, or a "Mark Back to Printing" override when it's
     currently Shipped.

  2. BULK on the orders list — a new "Mark Shipped" button in the
     selection action bar. Multi-select rows, click the button,
     confirm, done.

Every transition is logged in a new SQLite table for audit and
future "order history" features.

This is the foundation for Phases 30/31 (auto-detect ship via
ShipStation polling, and a barcode scan-out page).

═══════════════════════════════════════════════════════
HOW IT WORKS
═══════════════════════════════════════════════════════

ELIGIBILITY:
- Only orders currently in status 40 (Printing) can be marked
  Shipped via the normal path. Orders in Queue, Shipped, etc. are
  refused (or skipped in the bulk case).
- The override path (Mark Back to Printing) has NO eligibility
  check — it's the escape hatch for mistakes.

SETTINGS (server/config/processing-settings.json):
  shippedStatusId: 39          — what "Shipped" maps to
  shipEligibleFromStatusIds: [40]   — which statuses qualify

SERVER ENDPOINTS:
  POST /api/sytist/orders/:orderId/ship       (admin + operator)
  POST /api/sytist/orders/batch-ship          (admin + operator)
  POST /api/sytist/orders/:orderId/unship     (admin only)

AUDIT (new table):
  order_status_audit
    id, ts, order_id, from_status, to_status,
    source, user_id, notes

  Auto-created on first ship/unship; idempotent.
  Sources logged so far: 'manual', 'bulk', 'manual_override'
  (Phase 30 will add 'shipstation_auto', Phase 31 will add 'scan')

VERIFY AFTER DEPLOY
═══════════════════════════════════════════════════════

PER-ORDER:
  1. Open an order detail page for an order currently in Printing.
     Look for a new "Production Status" card between ProcessOrder
     and Shipping — it shows the status name and id, plus a green
     "Mark Shipped" button.
  2. Click "Mark Shipped" → confirmation modal → confirm. The
     order's status badge in the header should update on reload.
  3. With a now-shipped order, the card shows a ghost
     "← Mark Back to Printing" button. Click it → confirm with
     the danger-styled button → status reverts.
  4. For an order NOT in Printing (e.g. still in Queue), the card
     shows a muted message saying it must be in Printing first.

BULK:
  1. Open the orders list, filter by Production Status = Printing.
  2. Select 2-3 orders with checkboxes.
  3. A green "Mark Shipped (3)" button appears in the action bar.
  4. Click it → confirmation modal → confirm.
  5. After it runs, the list refreshes (rows that got shipped
     disappear from the Printing filter), and a toast appears
     bottom-right: "Shipped 3 · Skipped 0".
  6. To test the eligibility check: select a mix including some
     orders in Queue. The toast should say "Shipped 2 · Skipped 1"
     and "Show skipped details" reveals which order(s) and why
     ("not in Printing (status 0)").

AUDIT (optional manual check):
  Once you've done a few ship/unship actions, you can inspect:
    sqlite3 server/config/sytist-dashboard.db
    SELECT * FROM order_status_audit ORDER BY ts DESC LIMIT 10;
  Each row should show order_id, from→to status, source, and ts.
