Phase 13b — packaging rules engine (server + UI)

═══════════════════════════════════════════════════════
SCOPE
═══════════════════════════════════════════════════════

Direct port of PhotoDay's packaging engine, adapted to Sytist's
order shape. Replaces the manual carrier/service/weight/dims
form with rule-driven defaults that the operator can still
override per-order.

Two pieces in one tarball:

  13b-1: Server-side engine + integration
  13b-2: Settings → Packaging UI

═══════════════════════════════════════════════════════
WHAT'S IN THIS TARBALL
═══════════════════════════════════════════════════════

NEW FILES:
  server/services/packagingService.js
    The rule engine. Single public method:
      determinePackaging(order) → {
        packageType, packageTypeName,
        dimensions, weight, carrierCode, serviceCode,
        packageCode, notes[], itemWeights[]
      }
    Auto-creates server/config/packaging-config.json on first
    run with PhotoDay's defaults (SKU table identical between
    the two systems). Built-in `fs` only — no fs-extra.

  client/src/pages/settings/PackagingPage.js
    Five-section settings UI:
      1. Product weights table (SKU CRUD)
      2. Packaging types table (edit dims + base weight per type)
      3. Routing rules form (forcePackageSKUs, boxRouteSKUs,
         framedPanoSKUs, magnet threshold, slip weight + position)
      4. Package bundles table (Gold/Silver/Bronze CRUD)
      5. Test calculator — paste an order ID, see engine output
         including the rule trace ("Why this routing: …")

MODIFIED:
  server/services/shipstationService.js
    + Calls packagingService.determinePackaging in
      buildOrderFromSytist
    + Per-item weights from the engine are converted to grams
      and attached to each item in the SS payload (fixes the
      SS line-item-sum truncation issue)
    + Override > engine > app-settings defaults precedence
    + New previewPackagingForOrder() method returns the engine
      output for an order without building a full SS payload

  server/routes/shipstation.js
    + GET /orders/:orderId/status now includes packaging
      suggestion when the order is eligible
    + GET /packaging/config — return full config
    + PUT /packaging/config — replace top-level fields
    + PUT/DELETE /packaging/product-weights/:sku
    + PUT /packaging/types/:typeId
    + PUT/DELETE /packaging/bundles/:sku
    + GET /packaging/preview/:orderId — run engine on order

  client/src/pages/OrderDetailPage.js
    + ShippingBlock form pre-populates from engine output
      (when status.packaging is present)
    + Shows "💡 Engine suggests: <type> · <weight>oz ·
      <carrier>/<service>" banner above the form with the
      rule trace as a tooltip
    + Falls back gracefully to app-settings defaults when
      engine has no output (eligibility false, engine error,
      etc.)

  client/src/pages/settings/SettingsLayout.js
    + Sidebar link "Packaging" under Integrations

  client/src/components/AppLayout.js
    + Route /settings/packaging → PackagingPage

═══════════════════════════════════════════════════════
DESIGN DECISIONS WORTH NOTING
═══════════════════════════════════════════════════════

• Engine output OVERRIDES app-settings defaults in the form.
  Operator can still override per-order. Reasoning: the whole
  point of an engine is it knows more than a static default;
  if we keep showing the static defaults, the engine is mere
  decoration. The "💡 Engine suggests" line above the form
  makes WHY the form values look that way visible.

• Save buttons are per-section, not page-wide. Each table row
  has its own Save / Delete; routing rules section has a single
  Save for that section. This matches how the engine config is
  shaped (multiple independent concerns) and avoids the "save
  everything every time" pattern that's easy to mis-target.

• Test calculator lives ON the Settings page rather than as a
  separate route. Operators editing rules can immediately
  validate against a real order without context-switching.

• Package type IDs (flat_6x8, medium_box, etc.) are NOT
  editable in the UI — the engine references them by ID. To
  add a new packaging type you'd edit the JSON config directly.
  Could add a "New type" UI later if needed.

• Per-item weight encoding: ShipStation sums line-item weights
  when SKUs have Product Defaults stored. To stay accurate the
  engine emits per-line weights that total exactly the order
  weight. The packaging baseWeight + ceiling-rounding remainder
  gets rolled onto the first non-digital line item. Weights go
  out in GRAMS (integer) rather than oz (fractional) because
  ShipStation truncates fractional ounces per line.
