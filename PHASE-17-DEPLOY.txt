Phase 17 — Green-screen background compositing for non-composite SKUs

═══════════════════════════════════════════════════════
PROBLEM
═══════════════════════════════════════════════════════

The composite engine ALREADY handles green-screen backgrounds for
SKUs mapped to a composite layout (Memory Mate, etc.) — it consumes
backgroundPhoto via the playerBackground slot.

But for SKUs NOT mapped to a composite layout (regular 8x10, 5x7,
wallets, etc.), green-screen lines render with the transparent
subject directly. The imposition preview and the production print
both show the keyed-out subject with no background.

Visible in the imposition preview screenshot: figure surrounded by
the page background instead of the chosen photo backdrop.

═══════════════════════════════════════════════════════
WHAT THIS PHASE DOES
═══════════════════════════════════════════════════════

Adds a new green-screen compositing step that runs BEFORE imposition,
ONLY for line items that:
  - Are green-screen (flags.greenScreen === true)
  - Have a chosen background (backgroundPhoto.fullUrl is set)
  - Are NOT going through the composite engine (which already
    handles its own background)

For those lines:
  1. Download the chosen background from S3
  2. Resize it to fit the subject's dimensions using fit:'cover'
     (preserves aspect ratio, fills canvas, crops overflow)
  3. Composite the subject PNG on top
  4. Write the result back to the on-disk file, replacing the
     transparent PNG with the composited JPG

Downstream — imposition, packing slip thumbnails, Darkroom .txt —
naturally pick up the composited file because they all read from
the same path.

Also fixes the imposition PREVIEW endpoint to do the same compositing
before rendering the preview image, so what you see in the browser
matches what gets printed.

SECTION A — patch for server/services/processingService.js
═══════════════════════════════════════════════════════

Find the line that starts Step 2:

    // ─── Step 2: imposition in-place on every successfully-downloaded photo

Add this NEW block IMMEDIATELY BEFORE it (so the new code is Step
1.6, running after composite and before imposition):

```javascript
    // ─── Step 1.6 (Phase 17): green-screen background composite ──
    //
    // For line items that are green-screen (flags.greenScreen) AND
    // have a chosen background (backgroundPhoto) AND are NOT being
    // handled by the composite engine (skipImpositionCartIds), we
    // need to flatten the transparent subject onto the background
    // before imposition or the print shows up with the page color
    // visible behind the figure.
    //
    // The composite engine already handles its own backgrounds via
    // the playerBackground slot, so we skip those lines here to
    // avoid double-compositing.
    //
    // We overwrite the downloaded file at downloaded.path so Step 2
    // (imposition) and the slip thumb step pick up the composited
    // image with no other changes.
    const greenscreenService = require('./greenscreenService');
    for (const li of sub.lineItems) {
      const downloaded = photosByCartId[li.cartId];
      if (!downloaded) continue;
      if (skipImpositionCartIds.has(li.cartId)) continue;
      if (!greenscreenService.shouldComposite(li)) continue;

      try {
        const subjectBuffer = await fsp.readFile(downloaded.path);
        const { buffer: composedBuffer, warnings: gsWarnings } =
          await greenscreenService.composeWithBackground(
            subjectBuffer,
            li.backgroundPhoto.fullUrl,
            { outputFormat: 'jpeg', jpegQuality: 92 }
          );
        // Atomic .tmp + rename so partial writes never reach
        // downstream readers.
        const tmp = downloaded.path + '.gs.tmp';
        await fsp.writeFile(tmp, composedBuffer);
        await fsp.rename(tmp, downloaded.path);

        for (const w of gsWarnings || []) {
          subResult.warnings.push({
            type: 'greenscreen_' + (w.type || 'warning'),
            cartId: li.cartId,
            message: w.message,
          });
        }
      } catch (err) {
        subResult.warnings.push({
          type: 'greenscreen_compose_error',
          cartId: li.cartId,
          message: `Green-screen composite failed: ${err.message}`,
        });
      }
    }
```

That's the only change to processingService.js.

SECTION B — patch for server/routes/sytist.js
═══════════════════════════════════════════════════════

Find the imposition preview endpoint, which starts with:

    router.get('/imposition/preview/:orderId/:cartId', async (req, res) => {

Inside it, find this block:

```javascript
    const ctx = impositionService.buildContext(order, lineItem);
    const result = await impositionService.composeFromUrl(
      lineItem.photo.fullUrl,
      lineItem.sku,
      ctx,
      orientation
    );
```

REPLACE that whole block with:

```javascript
    const ctx = impositionService.buildContext(order, lineItem);

    // Phase 17: if this line is green-screen with a chosen
    // background, composite the background under the subject before
    // imposition. Otherwise feed the URL straight through as before.
    const greenscreenService = require('../services/greenscreenService');
    let result;
    if (greenscreenService.shouldComposite(lineItem)) {
      try {
        // Fetch the keyed-out subject first
        const subjectResp = await fetch(lineItem.photo.fullUrl);
        if (!subjectResp.ok) {
          throw new Error(`Failed to fetch subject: HTTP ${subjectResp.status}`);
        }
        const subjectBuffer = Buffer.from(await subjectResp.arrayBuffer());
        const { buffer: composedBuffer } =
          await greenscreenService.composeWithBackground(
            subjectBuffer,
            lineItem.backgroundPhoto.fullUrl,
            { outputFormat: 'jpeg', jpegQuality: 92 }
          );
        result = await impositionService.buildSheetBuffer(
          composedBuffer,
          lineItem.sku,
          ctx,
          orientation
        );
      } catch (gsErr) {
        // Fall back to subject-only on green-screen errors so the
        // preview still renders something. Log the warning so the
        // operator notices.
        console.warn(
          `[imposition/preview] greenscreen failed for ${req.params.orderId}/${req.params.cartId}: ${gsErr.message}`
        );
        result = await impositionService.composeFromUrl(
          lineItem.photo.fullUrl,
          lineItem.sku,
          ctx,
          orientation
        );
      }
    } else {
      result = await impositionService.composeFromUrl(
        lineItem.photo.fullUrl,
        lineItem.sku,
        ctx,
        orientation
      );
    }
```

Why we call `buildSheetBuffer` directly instead of `composeFromUrl`:
composeFromUrl fetches a URL. We already have the composited image
in memory as a Buffer, so we go one level lower and pass the Buffer
straight to buildSheetBuffer (which is what composeFromUrl calls
internally after the fetch).

That's the only change to routes/sytist.js.

═══════════════════════════════════════════════════════
EDGE CASES HANDLED
═══════════════════════════════════════════════════════

  - Background URL missing: warning logged, subject-only image
    used. Order keeps processing.

  - Background fetch fails: warning logged, subject-only image
    used. Order keeps processing.

  - SKU has composite mapping (skipImpositionCartIds): skipped.
    composite engine's playerBackground slot does the work.

  - Background and subject have different aspect ratios: background
    scales to cover the subject's dimensions, overflow cropped on
    the long axis. No blank pixels, aspect preserved.

  - Subject is already opaque (no actual transparency): composite
    still works — alpha=1.0 everywhere means subject fully covers
    background. Equivalent to original output.
