Phase 33 — Four-item bundle:
            1. Remove "Process order?" popup
            2. Reverse Phase 31 auto-push during SS adoption
            3. Manual "Push packaging to ShipStation" button + endpoint
            4. Extensive [SS]-tagged logging in processingService

═══════════════════════════════════════════════════════
ITEM 1 — POPUP REMOVAL
═══════════════════════════════════════════════════════

The window.confirm prompt that fired on every "Process this
order" click is gone. The button is prominent enough that the
confirm was just friction.

Other confirm prompts on the page are intentionally KEPT:
  - "Send order N to ShipStation?" (Send button)
  - "Delete this order from ShipStation?" (Delete button)
  - "Push current packaging to ShipStation?" (NEW Phase 33 button)
These are less-frequent destructive or external-side-effect
actions where confirmation is worth the friction.

═══════════════════════════════════════════════════════
ITEM 2 — REVERSE PHASE 31 AUTO-PUSH
═══════════════════════════════════════════════════════

Phase 31 pushed packaging to existing SS orders during the
adopt-existing path. Per operator preference ("reprocessing
should not be sent to ShipStation unless the user selects to"),
this is now reversed.

NEW behavior in _tryCreateShipStation when processing finds an
order ALREADY exists in SS (no local link yet, but SS has a
match by orderNumber):

  - Create the local link row pointing to the existing SS order
  - DO NOT call createOrder to push packaging
  - Return reason='adopted_existing' message="...(skipped auto-push)"

The link row's carrier/service/package metadata uses whatever
the existing SS order has, falling back to the freshly-computed
payload values if SS didn't echo them.

If the operator wants to push packaging to that adopted SS
order, they use the new manual button (Item 3 below).

═══════════════════════════════════════════════════════
ITEM 3 — MANUAL "PUSH PACKAGING TO SHIPSTATION"
═══════════════════════════════════════════════════════

NEW endpoint:
  POST /api/sytist/orders/:orderId/push-packaging
  - Requires existing link
  - Builds fresh payload from current Sytist state
  - Calls shipstationService.createOrder({...payload, orderId: link.ss_order_id})
  - Updates local link row's carrier/service/package codes to
    reflect what was pushed
  - Returns the SS response details

NEW button in the order detail page:
  Inside the LinkedShippingPanel (visible when order is linked
  to a SS order, but not yet shipped). Sits in the button row
  next to "Re-fetch status" and "Mark shipped". Click → confirm
  modal → calls the endpoint → success/error banner appears
  under the button row.

UI label: "Push packaging to ShipStation"
Tooltip:  "Recompute packaging and push to ShipStation
           (overwrites SS-side weight/carrier/package)"

═══════════════════════════════════════════════════════

All [SS]-tagged log lines now appear in the server console

       packageCode=large_envelope carrier=stamps_com/usps_first_class_mail weight=4

For an adopt-existing case (Item 2 path):

  [SS] 110684: _tryCreateShipStation entered
  [SS] 110684: payload built — weight=4oz, ...
  [SS] 110684: calling listOrders to check for phantom
  [SS] 110684: listOrders returned 1 match(es)

       orderNumber, adopting WITHOUT pushing packaging (Phase 33 default)

For the already-linked skip:

  [SS] 110684: _tryCreateShipStation entered
  [SS] 110684: PATH=already_linked, SS#525371639 ss_status=awaiting_shipment —
       skipping create. Use "Push packaging to ShipStation" button
       to opt-in re-push.
