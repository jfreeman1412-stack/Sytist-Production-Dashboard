Phase 34 — Green-screen compositing for the Process flow
            (imposition + packing slip)

═══════════════════════════════════════════════════════
THE BUG THIS FIXES
═══════════════════════════════════════════════════════

Sytist line items with cart_photo_bg > 0 are flagged as
green-screen, meaning the customer chose a background image for
their transparent (keyed) photo. The dashboard's
greenscreenService composites the subject onto the background.

BEFORE Phase 34:
  - The MANUAL preview endpoints in routes/sytist.js called
    greenscreenService correctly.
  - The MANUAL save endpoint for a single line item called it
    correctly.
  - But the FULL "Process this order" flow did NOT.

So when the operator processed an order with green-screen items:
  - Memory Mate (uses a composite layout with playerBackground
    slot) → got its background via the composite engine ✓
  - Mini Magnets / wallets / plain prints (uses impositionService
    directly) → printed with NO background, just the keyed
    transparent subject on white ✗
  - Packing slip thumbnails → also no background, showed raw
    keyed photos ✗

AFTER Phase 34:
  - New "Step 1.4" in processOrder composites green-screen line
    items right after photo download.
  - The composed file is written to disk as <photo>_composed.jpg
    and downloaded.path is updated to point at it.
  - Imposition reads this composed file → printed sheets now
    have the background.
  - Packing slip receives a composedByCartId map of disk paths
    → its thumbnails use the composed file instead of fetching
    thumbUrl → slip matches the actual print.
  - Composite-mapped line items (Memory Mate) are SKIPPED in
    Step 1.4 because they have their own playerBackground slot
    in the composite engine. No double-compositing.

═══════════════════════════════════════════════════════
ARCHITECTURE
═══════════════════════════════════════════════════════

The compose step runs ONCE per cartId, after Step 1 (download)
and before Step 1.5 (composite engine). It produces a single
composed JPG on disk:

  Z:\Photo Day\__Open Orders\Sytist_Orders\
    110685_481629_JV_Baseball-0016.png       ← original transparent
    110685_481629_JV_Baseball-0016_composed.jpg  ← Phase 34 output

Downstream code (imposition, packing slip) reads from the
composed file. Sharing one composed file across imposition +
packing slip avoids duplicate work and guarantees they show the
same thing.

Failure mode: if compose fails (network, bad URL, etc.), the
original file is left in place and a warning is logged. The
order still processes — better a missing background than a
missing item. The warning surfaces in the processing result UI
as type='greenscreen_compose_error'.

═══════════════════════════════════════════════════════
KNOWN LIMITATIONS / FUTURE WORK
═══════════════════════════════════════════════════════

  - The composed file replaces the original in downloaded.path.
    If any downstream code expected the raw transparent PNG
    (other than the composite engine, which we explicitly skip),
    it'll see the composed file. We checked the major paths
    (imposition, .txt writer, packing slip) and they all just
    need a printable image — the composed file is correct.

  - If you switch backgrounds on an already-processed order and
    reprocess, the composed file gets overwritten with the new
    background. Atomic via .tmp+rename so there's no
    half-written state.

  - The composeWithBackground output is JPEG quality 92,
    flattened onto the resized background. This matches the
    preview path. If you want PNG for the composed output
    (slightly larger, lossless), change `outputFormat: 'jpeg'`
    to `'png'` in processingService.js Step 1.4.
